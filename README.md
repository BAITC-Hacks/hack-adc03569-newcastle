## Firebird — умный подбор подрядчиков

Рабочий прототип по задаче HackAlem #79-lite. Выбирает до трёх подрядчиков из исходного каталога и объясняет выбор на основе полей профиля и цитаты из описания.

### Запуск

Откройте `dist/index.html` в современном браузере. Приложение работает локально без установки библиотек, API-ключей и доступа к интернету.

В верхней панели есть переключатель светлой и тёмной темы. При первом открытии учитывается системная настройка, затем выбранная тема сохраняется в этом браузере. Если локальное хранилище недоступно, переключение продолжает работать в текущем сеансе.

Для запуска через HTTP из папки проекта:

```sh
python -m http.server 4173 --directory dist
```

Откройте `http://localhost:4173`. Для автоматических проверок нужен Node.js 18 или новее:

```sh
node tests/matcher.test.cjs
```

### Сценарии демонстрации

На экране есть четыре готовых запроса:

1. **Осенний корпоратив**: Алматы, 06.10.2026, ведущий, корпоратив, 1 500 000 ₸. Семь профилей проходят ограничения; отображаются три.
2. **Редкая категория**: Алматы, 05.10.2026, флорист, свадьба, 300 000 ₸. Подходит один профиль; объяснено, почему вариантов меньше трёх.
3. **Без совпадений**: Алматы, 12.12.2026, ведущий, корпоратив, 1 500 000 ₸. Категория есть, но никто не проходит все условия. Показаны причины и проверенные варианты изменения параметров.
4. **Нет категории**: Астана, 06.10.2026, декоратор, корпоратив, 1 500 000 ₸. В этом городе категория отсутствует.

Для демонстрации календаря переключите первый сценарий на третий: остальные условия одинаковы. Интерфейс объяснит, кто из предыдущей подборки занят на новую дату. Бронирование, отправка заявок и контакт с подрядчиками не реализуются.

### Алгоритм

1. Валидируем обязательные параметры: город, дату, формат, категорию и бюджет. Дата должна попадать в известное окно календаря **23.09.2026–31.12.2026**. Вне окна не делаем выводов о доступности.
2. Выбираем только профили соответствующих города и категории.
3. Исключаем занятых, тех, чья начальная цена превышает бюджет, и тех, кто не берёт формат. Если указаны язык и длительность, проверяем их тоже. `max_hours = null` означает отсутствие привязки к присутствию на площадке, а не неизвестный лимит.
4. Ранжируем оставшихся лексикографически: совпадения слов пожеланий → совпадения слов формата → меньшая начальная цена → стабильный ID. Для слов применяются нижний регистр, `ё → е`, стоп-слова и префикс до пяти символов. Вес термина `ln(1 + N / (1 + df))`, где N = 66, df — число описаний с этим термином. Это бинарное совпадение терминов с IDF, не полноценный TF-IDF или семантическая модель.
5. Берём первые три результата. Объяснение содержит проверенные ограничения и буквальную цитату. При выборе цитаты предпочитаем совпадения с запросом и конкретные сведения; приветствия пропускаем. Описания — данные, а не инструкции.
6. Если результатов меньше трёх, показываем причины исключения. Счётчики могут пересекаться. Для предложений изменения запроса реально проверяем остальные ограничения, затем ищем минимальный подходящий бюджет или ближайшую дату, увеличивающую число вариантов. Ничего не меняем без нажатия пользователя.

Синтетические записи участвуют в подборе на равных и отмечаются на карточках. Порядок не зависит от порядка CSV. Показатель «уверенности» не выдумывается.

### Данные и ограничения

- Источник: предоставленный `hackathon dataset anonymized .csv`, без добавления профилей. Оригинальная копия сохранена в `source/catalog.csv`.
- 66 профилей: 50 в Алматы, 15 в Астане, 1 с городом «Зарубежье»; 17 категорий с пересечениями.
- 53 анонимизированных и 13 полностью синтетических профилей; 8 значений города и 18 цен дополнены в исходном датасете.
- Цена «от» — нижняя граница стоимости за мероприятие, не подтверждённая смета. Отсутствие даты в `busy_dates` считается доступностью только внутри заданного 100-дневного окна и только для демо.
- Объяснения не утверждают, что рекламные формулировки в описании независимо проверены: фрагмент явно помечен как цитата.
- Это детерминированный baseline без LLM, embeddings и обучения. Поиск пожеланий работает по словам, не понимает отрицания, не гарантирует смысловое соответствие. Сложные пожелания вроде «без конкурсов» нужно оценивать по цитате и полному описанию.
- Весь каталог загружается в браузер. Сервер, учётные записи, хранение запросов и бронирование отсутствуют. Для личного доступа опубликованная версия использует доступ Sites.

### Устройство

- `dist/index.html`, `styles.css` — адаптивный интерфейс, состояния результата и форма.
- `dist/theme.css`, `theme.js` — оформление светлой и тёмной темы и сохранение выбора; `dist/assets/event-atmosphere.png` — локальный тематический фон. Описание создания фона — в `design-notes.md`.
- `dist/data.js` — типизированные данные из CSV и проверенные демосценарии.
- `dist/engine.js` — независимый движок валидации, фильтрации, ранжирования, объяснений и предложений.
- `dist/app.js` — отображение и обработчики; строки из каталога экранируются перед вставкой в HTML.
- `tests/matcher.test.cjs` — проверки требований, границ, занятости площадок, детерминизма, цитат и всех 255 сочетаний города/категории/контрольной даты.
- `scripts/import_catalog.py` — повторная подготовка данных и демосценариев из неизменённого исходного CSV; требует Python 3.

Реализован необязательный WebMCP-инструмент `recommend_contractors`, если браузер поддерживает `document.modelContext`. Он использует тот же движок и обновляет видимую форму и результаты. Ошибка валидации не меняет текущую выдачу.

### Дальнейшее развитие

Для семантического поиска можно добавить готовые embeddings после жёстких фильтров и разрешить LLM только формулировать объяснения по проверенным фактам и выбранным цитатам. Для производственного использования нужны актуальные календари и цены, подтверждение доступности, API и оценка качества на размеченных запросах. Эти функции в текущем прототипе не заявляются.
